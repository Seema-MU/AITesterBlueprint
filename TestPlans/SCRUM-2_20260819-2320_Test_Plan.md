# 1. Document & Release Overview

## 1.1 Purpose

This Test Plan defines the QA strategy, scope, test approach, risks, and release criteria for validating the fix for **JIRA SCRUM-2** ("no error message showed when invalid credentials entered", Priority: Medium, Type: Bug, Status: To Do).

The bug: when a user enters invalid credentials on the VWO login page and clicks **Sign in**, no error message is displayed — the user gets no feedback on why the login failed.

## 1.2 Release Overview

Per the ticket, the repro is:

1. Open `https://app.vwo.com/#/login`
2. Enter invalid credentials
3. Click **Sign in**
4. **Actual:** No error message displayed
5. **Expected:** (left blank in the ticket)

This release validates the fix for the missing invalid-credentials error and confirms the broader login error-handling paths still work.

# 2. Objectives & Scope

## 2.1 Test Objectives

* Verify the fixed build displays a clear error message when invalid credentials are submitted.
* Verify the error appears in the correct location, with correct text/formatting, and doesn't leak sensitive info.
* Verify the error path across credential variations: wrong password, unknown email, malformed email, empty fields.
* Verify the fix doesn't regress valid login, Remember Me, password visibility toggle, or alternate sign-in options.
* Verify no error message is shown on successful login.

## 2.2 In Scope

### Functional

* Invalid-credentials error message display (the fix)
* Error-message variations: wrong password / unknown user / malformed input / empty fields
* Successful login shows no error (regression guard)
* Remember Me checkbox behavior
* Password visibility toggle
* Forgot Password link, Google/SSO/Passkey buttons, Free Trial CTA remain functional (regression)

### Integration

* Error display does not break VWO dashboard handoff after successful login
* Analytics events for login failure still fire

### Platforms

* Browsers: Chrome, Edge, Firefox, Safari (desktop)
* Mobile: iOS Safari, Android Chrome (responsive)

### Non-Functional

* Performance: No — page-load not in scope for a bug-fix validation
* Security: Yes (error message must not leak whether email exists / reveal account details)
* Accessibility: Yes (error message must be announced to screen readers, visible focus)
* Compatibility: Yes (browser matrix above)

## 2.3 Out of Scope

* Password reset / Forgot Password full flow (covered in SCRUM-1 plan)
* Google / SSO / Passkey authentication behavior (separate flows)
* Backend auth-service implementation details
* Performance/load testing

# 3. Product & Quality Risk Overview

## 3.1 Product Overview

* **Application:** VWO login page at `https://app.vwo.com/#/login`
* **Flow under test:** User submits invalid credentials → system must surface a clear error
* **User types:** Marketers, PMs, developers, enterprise users (SSO)
* **External systems:** Auth backend; Google/SSO/passkey providers (out of scope here)

## 3.2 Critical Business Flows

* Invalid login → visible, clear error message
* Valid login → dashboard handoff with no error
* Login attempts while auth backend is slow/unavailable → graceful feedback

## 3.3 Quality Risks

| Risk | Impact | Probability | Risk Level | Mitigation |
| ---- | ------ | ----------- | ---------- | ---------- |
| Error message leaks account existence (user enumeration) | High | Medium | High | Verify generic message wording (per screenshot: "email, password, IP address or location did not match") |
| Error shown but not announced to screen readers | Medium | Medium | Medium | A11y check with screen reader |
| Fix introduces regression to valid login | High | Low | Medium | Regression on happy path |
| Error message not localized / formatted badly | Low | Low | Low | Visual check across browser matrix |

## 3.4 Risk-Based Testing Prioritization

Highest priority: the fix itself (error shows on invalid credentials) and security (no user enumeration). Then regression of the happy path, then a11y/compatibility.

# 4. Test Strategy

## 4.1 Overall Testing Approach

Risk-based functional validation of the bug fix plus targeted regression of the login happy path and error variants. Primarily UI/E2E; API-level check only where it informs the UI behavior.

## 4.2 Test Levels

| Test Level | Purpose | Primary Owner |
| ---------- | ------- | ------------- |
| Unit Testing | Validate error-handling component | Development |
| API/Service Testing | Validate auth endpoint error responses | QA/Development |
| Integration Testing | Validate error surfaces through UI | QA/Development |
| System Testing | Validate complete login behavior | QA |
| End-to-End Testing | Validate repro steps end to end | QA |

## 4.3 Test Types

Functional, Integration, Regression, Smoke, API, UI, Exploratory, Compatibility, Security (error-message wording), Accessibility (screen reader).

## 4.4 Test Design Approach

* Positive (valid login, no error)
* Negative (invalid credentials variants → error message appears)
* Boundary (empty fields, whitespace-only, max-length)
* Error handling (backend failure, network timeout)
* Accessibility (error announced, aria-live region)
* Exploratory around the repro steps

## 4.5 Regression Strategy

Focus on: valid login path, Remember Me, password toggle, alternate sign-in buttons present/enabled, and dashboard handoff. Keep the suite small — this is a targeted bug-fix validation.

# Gaps & Questions for the author

Findings from the requirement gap-analysis (✅ present / ⚠️ ambiguous / ❌ missing).

## ❌ Missing / blocking

1. **The "Expected" field in the ticket is blank.** The repro says "expected:" with nothing after it. The implied expectation is "an error message is shown" — confirmed by the attachment, which shows "Your email, password, IP address or location did not match". Please confirm this is the expected text, or specify the exact wording.
2. **Screenshot contradicts the bug report.** The attachment `image-20260819-165643.png` actually shows the error message displayed (red-bordered alert with the warning text) and the email field filled with `seema`. If the screenshot is from the fixed build, the bug may already be resolved — or the error appears only under some conditions. Which build was the screenshot taken from?
3. **No test accounts/environments defined.** Provide a valid test account and confirm whether `https://app.vwo.com` is live or a test mirror.

## ⚠️ Ambiguous

4. **Input format:** the email field in the screenshot contains `seema` (no domain). Is that a valid accepted format (username login), or was it an invalid-format input that itself should trigger a validation error?
5. **Message variations:** should the error differ between "wrong password" and "unknown email" (security best practice says no), or is one generic message intended for all failures?
6. **Where the message should appear** — top of form (as in screenshot) vs inline per-field. Confirm placement.
7. **Browser/device scope for the fix** — was the bug reproduced on all browsers or one? Confirm the matrix to test.

## ✅ Present (usable as-is)

- Repro steps (open URL → enter invalid credentials → click Sign in)
- Actual behavior stated (no error message)
- Screenshot attachment showing the intended error state
- Priority (Medium) and type (Bug) defined
